# Event Scheduler

カンファレンスのセッション管理・スタッフ配置を行うWebアプリケーション。

## 利用方法

### スタッフ登録とログイン

管理者が `/accounts` にメールアドレスを登録したら、スタッフ本人が `/register` で同じメールアドレスを入力します。届いたリンクを確認し、Google または LINE を連携すると登録完了です。次回以降は `/login` から連携したアカウントでログインします。管理者はスタッフや他の管理者を追加できます。

### 管理者の基本的な流れ

1. **部屋を登録** — 会場の部屋名・収容人数を設定
2. **セッションを登録** — セッショングループ（日程）ごとに、タイトル・時間・部屋を設定。LT・パネルディスカッションは複数登壇者に対応
3. **スタッフを登録** — 名前・スキル・対応可能時間帯・希望セッションを設定
4. **スタッフを配置** — 手動配置、または自動配置アルゴリズムで一括割り当て
5. **確認・エクスポート** — 全体スケジュール・スタッフ別詳細で確認し、Excel出力

### 主な機能

| タブ | 内容 |
|------|------|
| 全体スケジュール | 全セッション・配置表の表示 |
| スタッフ別詳細 | スタッフごとの担当一覧 |
| 会場 | 会場地図の表示 |
| 全体スケジュール管理 | セッションの追加・編集・削除 |
| スタッフ管理 | スタッフの登録、希望・可用時間の編集、スタッフ別の担当表表示 |
| 部屋管理 | 部屋の追加・編集・削除 |
| 会場地図 | フロアマップ画像のアップロード |
| 配置アルゴリズム | スキル・希望・バランスを考慮した自動配置 |
| エクスポート | Excel出力、connpassタイムライン・登壇者テンプレート生成 |
| 公開API | スケジュールJSONの外部配信、Webhook・GitHub Actions連携 |
| バックアップ | 自動バックアップ（間隔/毎日）、手動バックアップ、リストア、履歴管理 |
| 設定 | アプリタイトル、カテゴリ管理、セッショングループ管理、データ初期化 |

### セッション形式

デフォルトで以下の形式が用意されています。設定画面から追加・編集・削除が可能です。

- **通常セッション** — 1人の登壇者による発表
- **LT（ライトニングトーク）** — 複数登壇者を登録可能
- **パネルディスカッション** — 複数登壇者を登録可能

### 公開API

イベント公式サイト等の外部サイトからスケジュールデータをJSON形式で取得できるAPIを提供します。

- **スナップショット方式** — 「パブリッシュ」で確定したデータのみ公開。編集中のデータは外部に漏れません
- **APIキー認証** — クエリパラメータまたはヘッダーで認証
- **Webhook** — パブリッシュ時に任意のURLへPOST通知
- **GitHub Actions連携** — パブリッシュ時にworkflow_dispatchを自動実行し、GitHub Pages等のキャッシュを更新
- **パブリッシュ履歴** — 過去のスナップショットに切り替え可能

### 自動配置アルゴリズム

スタッフの希望・スキル・対応可能時間・負荷バランスをスコアリングして最適な配置を算出します。配置後に手動で調整も可能です。

**自動配置は日程ごとに実行します。** 日程タブで日付を選ぶと、その日の全セッション（セッション担当・受付案内・懇親会など全カテゴリ）がまとめて配置されます。全日程を一括で配置する機能はありません。

- 活動可能時間・時間重複・移動時間・最大稼働時間（`max_hours`）といったハード制約と、負荷の平準化は **1日単位** で適用します
- 日をまたいだ担当の偏りは、ハード制約ではなくスコアのソフトな減点として考慮します
- 他の日の配置は書き換えません。3日開催なら3回実行してください

### オフライン利用

ログイン後にオンラインで画面を開くと、端末に担当表と画像を保存します。全体スケジュール、スタッフ別担当、場所ごとの担当表はオフラインでも参照できます。編集と保存には接続が必要です。共有端末では利用後にログアウトしてください。

## 開発環境

Next.js のページと Route Handlers を OpenNext で Cloudflare Workers に配置します。部屋・セッション・スタッフ・配置・設定は D1、写真・会場地図・バックアップ・公開スナップショットは非公開の R2 バケットに保存します。Worker の Cron Trigger がバックアップ設定を5分ごとに確認します。

Node.js 24 と npm を使います。ローカル環境は Wrangler の D1 と R2 で動作します。

```sh
make install
cp web/.dev.vars.example web/.dev.vars
# 初回は自分の開発用メールアドレスを指定する
INITIAL_ADMIN_EMAIL=admin@example.test make dev
```

利用するプロバイダーの開発用設定を `web/.dev.vars` に記入します。初回の `make dev` が指定メールを管理者として D1 の名簿に追加します。ブラウザで `http://localhost:3000/register` を開き、そのアドレスで初回登録してください。次回以降は `make dev` のみで起動できます。`APP_ORIGIN` にはブラウザで実際に開く URL を設定します。Firebase をローカルで試す場合は `localhost` を承認済みドメインに加えてください。Wrangler のローカルメール送信はシミュレーションで、登録用メールをローカルで確認できます。[メール・Google・LINE の設定](.github/workflows/README.md#スタッフ個別ログインの準備)・[Wrangler のローカルメール確認](https://developers.cloudflare.com/email-service/observability/local-development/sending/)

| コマンド | 用途 |
|---|---|
| `make test` | TypeScript、スケジューラ、D1・R2 のテスト |
| `make preview` | 本番形式のバンドルをビルドし、ローカル Worker で確認 |
| `make deploy ENV=staging` | GitHub Actions から staging をデプロイ |
| `uv sync --frozen && uv run pytest` | 移行前の Python 実装の回帰テスト |

## 配置と既存データの移行

`main` の変更は staging、GitHub Release の公開は production に配置します。各環境は専用の Worker・D1・R2 を使用します。Cloudflare アカウントの指定、GitHub のシークレット設定、既存 SQLite・アップロードの移行と切り戻しは[デプロイ手順](.github/workflows/README.md)を参照してください。

移行元の Python アプリは `app/`、Vue フロントエンドは `frontend/` にあります。Azure の既存環境を操作する場合はリポジトリのルートで `make -f infra/Makefile.azure help` を実行します。
